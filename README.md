# REDSTOCKS
### A Full-Stack Fintech & Stock-Market Paper-Trading Platform

> **REDSTOCKS** is a full-stack stock-market research and paper-trading web application inspired by Groww's approachable investing experience, Quadency's information-rich trading dashboard, and a restrained One Piece-inspired palette of crimson, ocean blue, and treasure gold.

**Project status:** In development — core platform (Phases 0–10) implemented and verified locally; deployment pending  
**Frontend:** React.js, Vite, JavaScript, HTML5, CSS3  
**Backend:** Node.js, Express.js  
**Database:** MongoDB, Mongoose  
**Database GUI:** MongoDB Compass  
**Deployment target:** Render (frontend and backend), MongoDB Atlas (database)

> **Important:** REDSTOCKS is intended for market research and simulated trading with virtual money. It does not place real orders with a broker or exchange. Never label sample, cached, or delayed data as live market data.

## Implementation status snapshot (updated 2026-10-26)

All market data is **demonstration data** generated by the built-in `demo` provider (no API keys required), labelled as such on every surface. Verified with a 29/29-passing HTTP smoke suite (`server/scripts/smoke-test.js`) and a manual browser walkthrough.


## 1. Project Overview

REDSTOCKS is a modern fintech web application for exploring stock-market information and learning how portfolio management and trading work through simulated transactions.

The application combines:
- **Groww-inspired usability:** straightforward navigation and readable financial information.
- **Quadency-inspired dashboard design:** structured panels, charts, watchlists, market summaries, and a data-rich trading workspace.
- **Original REDSTOCKS identity:** a dark interface with crimson branding, ocean-blue surfaces, and restrained treasure-gold highlights inspired by One Piece's adventurous atmosphere.

The application should be suitable for a full-stack academic project. Its key technical requirement is real integration between the React frontend, Node.js/Express backend, and MongoDB database.

### Core user journey

1. A visitor opens the landing page.
2. The user explores the market overview and searches for a stock.
3. The user opens a stock details page and reviews available price data.
4. The user registers or logs in to save a personal watchlist and portfolio.
5. The user makes a simulated buy or sell transaction using virtual money.
6. The backend validates the transaction and saves the resulting records in MongoDB.
7. The user reviews holdings, portfolio performance, and transaction history.

## 2. Goals and Scope

### Primary goals
- Build a polished, responsive React interface.
- Develop a modular Express API.
- Persist application data in MongoDB.
- Inspect collections and records through MongoDB Compass.
- Support user-specific watchlists and simulated portfolios.
- Validate virtual trades on the backend.
- Clearly identify the source and freshness of market data.
- Maintain an organized GitHub repository.
- Document local development, testing, and deployment.

### Scope boundaries

The initial product is a **paper-trading and market-research application**.

It does not:
- Execute real stock-market orders.
- Connect to a user's brokerage account by default.
- Accept deposits or withdrawals.
- Provide guaranteed investment returns.
- Guarantee that market data is real-time.
- Replace professional financial advice.

Authentication, news integration, administrative tools, and advanced analytics should be implemented according to the phase plan and available provider services.

## 6. Architecture

### High-level data flow

```text
┌───────────────────────────────────┐
│          React Frontend           │
│ Dashboard, Markets, Charts, Forms │
└─────────────────┬─────────────────┘
                  │ HTTP / JSON
                  ▼
┌───────────────────────────────────┐
│       Node.js + Express API        │
│ Routes → Middleware → Services     │
│ Validation, Auth, Trade Calculations│
└──────────┬─────────────────┬──────┘
           │                 │
           ▼                 ▼
┌────────────────────┐  ┌─────────────────────┐
│ MongoDB / Mongoose │  │ Market Data Provider│
│ Users, Watchlists, │  │ Quotes, History,    │
│ Portfolios, Trades │  │ News if supported   │
└────────────────────┘  └─────────────────────┘
           ▲
           │ Inspection and administration
           ▼
     MongoDB Compass
```

### Architectural rules
- The frontend communicates with the backend through APIs.
- The backend accesses MongoDB using Mongoose.
- The backend owns authoritative financial calculations.
- Market-provider credentials remain on the server.
- The frontend never connects directly to MongoDB.
- User-specific resources must be protected by authentication and authorization.
- Market data must be labelled as live, delayed, cached, or demonstration data accurately.
- Use a provider abstraction so integrations can change without rewriting every UI component.

## 9. Database Design

The following collections are proposed. Final schemas should reflect the implemented features.

### Users
Possible fields: `_id`, `name`, `email`, `passwordHash`, `role`, `createdAt`, `updatedAt`.

Requirements:
- Normalize email addresses.
- Enforce unique email.
- Hash passwords.
- Validate input.
- Prevent public role escalation.

### Stocks
Possible fields: `_id`, `symbol`, `companyName`, `exchange`, `industry`, `market`, `currency`, `description`, `providerSymbol`, `createdAt`, `updatedAt`.

A stock metadata record does not prove that its quote is current.

### Watchlists
Possible fields: `_id`, `userId`, `stockId`, `createdAt`.

Use a uniqueness constraint or equivalent protection to prevent duplicate user/stock entries.

### Portfolios
Possible fields: `_id`, `userId`, `virtualCashBalance`, `currency`, `createdAt`, `updatedAt`.

Never accept a client-supplied balance as authoritative.

### Holdings
Possible fields: `_id`, `userId`, `stockId`, `quantity`, `averageCost`, `createdAt`, `updatedAt`.

Choose whether holdings are derived from transactions or maintained separately. If stored separately, keep holdings, cash, and transactions consistent using supported MongoDB transaction mechanisms or a documented safe alternative.

### Transactions
Possible fields: `_id`, `userId`, `stockId`, `type`, `quantity`, `executionPrice`, `transactionValue`, `fees`, `status`, `marketDataTimestamp`, `createdAt`.

All authoritative financial values must be calculated or validated by the backend.

### Optional market-data cache
Possible fields: symbol, provider, quote snapshot, timestamp, expiration metadata. Cache only what is necessary and permitted by the provider.

### Optional news collection
Possible fields: source, headline, article URL, publication timestamp, related symbols, permitted summary, cache metadata. Respect attribution and content-retention terms.

## 16. Security and Financial Integrity

### Authentication and data protection
- Hash passwords with a suitable password-hashing algorithm.
- Protect private endpoints.
- Validate resource ownership.
- Avoid returning password hashes.
- Do not expose environment variables.
- Configure CORS deliberately.
- Limit request sizes.
- Validate input.
- Use appropriate rate limiting.
- Avoid leaking stack traces or internal secrets in production errors.
- Do not allow users to assign themselves admin roles.

### Paper-trading integrity

For a buy:
1. Authenticate the user.
2. Validate the stock and quantity.
3. Obtain an allowed price snapshot.
4. Calculate transaction value on the server.
5. Check virtual cash.
6. Update cash and holdings consistently.
7. Record the transaction.

For a sell:
1. Authenticate the user.
2. Validate the stock and quantity.
3. Check holdings.
4. Obtain an allowed price snapshot.
5. Calculate transaction value on the server.
6. Update cash and holdings consistently.
7. Record the transaction.

Do not trust client-supplied prices, totals, balances, holdings, or profit/loss.

Use MongoDB transactions when the deployment supports them and the operation requires atomic updates. Otherwise, document and implement an appropriate consistency strategy.

Define how the application handles fractional shares, rounding, fees, average cost, realized profit/loss, invalid or stale prices, and duplicate submissions.

## 20. Troubleshooting

### Backend cannot connect to MongoDB
- Check `MONGODB_URI`.
- Verify the database user and password.
- Verify Atlas network access.
- Check whether special characters in credentials require URL encoding.
- Inspect server logs without printing secrets.

### Frontend API requests fail
- Check `VITE_API_BASE_URL`.
- Verify that the backend is running.
- Check CORS settings.
- Inspect the browser Network tab.
- Verify endpoint path and HTTP method.

### Atlas connection works locally but fails on Render
- Check deployed environment variables.
- Verify Atlas network configuration.
- Check deployment logs.
- Ensure the service is not using a local-only MongoDB URI.

### Prices are missing
- Verify provider configuration.
- Check symbol and exchange support.
- Review rate limits.
- Confirm that the requested historical interval is supported.
- Show an honest unavailable-data state rather than fabricated values.

### Portfolio totals do not reconcile
- Check transaction history.
- Check holdings updates.
- Check cost-basis and rounding rules.
- Verify that cash, holdings, and transactions are updated consistently.
- Add regression tests for the failing case.

### A page fails after refreshing a direct URL
- Check React Router configuration.
- Configure the hosting provider's SPA rewrite rules if required.
